# 멀티 에이전트 설계 패턴 5가지 (LangChain + LangGraph)

> **한눈에 보기**
> - 하나의 LLM이 다 하지 않고 **역할이 나뉜 여러 에이전트가 협업**하는 5가지 패턴을 GPT(gpt-4o-mini)와 Gemini(gemini-3.5-flash-lite)로 구현했다
> - ① 순차(리서처 → 작성자) ② 라우터(`with_structured_output` 분류 → 전문가) ③ 감독자(`Command(goto=...)` + `create_agent` 하위 에이전트) ④ Map-Reduce(`Send`로 관점별 병렬 리뷰) ⑤ 작성자·비평가 루프 + 사람 승인(`interrupt`)
> - **각 노드가 무엇을 보게 할지 정하는 것**(컨텍스트 설계)이 핵심. 작성자는 리서처의 결과만, 하위 에이전트는 감독자의 작업 지시만 받는다
> - 마지막에 `create_agent` + 미들웨어로 되는 범위와 LangGraph가 필요해지는 경우를 비교했다
> - 실행 결과에서 본 것: 감독자가 계산을 **스스로** 해 버림, 병렬 결과 순서는 보장되지 않음, 사람 피드백 후 비평가 점수가 오히려 7점에 머묾, 미들웨어 호출 제한에 걸려 **답 없이 종료**

- 코드: [`exam13.ipynb`](exam13.ipynb) (강사님 자료 `fwedu/exam13.ipynb` 사본, 강의 슬라이드 이미지 포함, 📝 정리 셀 추가)
- 같은 날: [다중 LLM과 ReAct (LangGraph)](다중LLM과ReAct_LangGraph.md) · [오케스트레이션 패턴과 LangSmith](오케스트레이션패턴과LangSmith.md)

> 💡 Gemini 응답의 `content`는 문자열이 아니라 블록 리스트로 올 때가 있어 노트북 전체에서 `message.text`로 꺼낸다.

## 예제 ① 순차 협업: 리서처 → 작성자

```python
class PipelineState(TypedDict):
    topic: str
    research: str     # 리서처(gpt)가 채움: 핵심 사실 5개
    article: str      # 작성자(gemini)가 채움: 블로그 글
```

- 작성자는 사용자의 원래 질문이 아니라 **리서처가 남긴 `research`만** 읽는다. 각 노드에 무엇을 넘길지 정하는 것이 멀티 에이전트 설계의 출발점이다.

## 예제 ② 질문 라우터: 전문가에게 나눠 보내기

```python
class Route(BaseModel):
    category: Literal["code", "writing", "general"]
    reason: str                     # 왜 그렇게 분류했는지 (디버깅용)

router_llm = gpt.with_structured_output(Route)
def route_to_expert(state) -> str:
    return {"code": "code_expert", "writing": "writing_expert"}.get(state["category"], "general_expert")

builder.add_conditional_edges("router", route_to_expert,
    ["code_expert", "writing_expert", "general_expert"])   # 갈 수 있는 경로를 적어야 그림에 화살표가 그려진다
```

| 질문 | 분류 |
|---|---|
| 파이썬 리스트 중복을 순서 유지하며 제거 | code → `dict.fromkeys()` 예제 |
| '회의가 진행되어지겠습니다' 고쳐줘 | writing → 이중 피동 설명 |
| 오늘 저녁 메뉴 추천 | general |

- 라우터는 **판단만**, 전문가는 **답변만** 한다. 분류처럼 틀리면 안 되는 일은 `Literal` 구조화 출력으로 값의 범위를 막는다.

## 예제 ③ 감독자(Supervisor)와 도구 사용 에이전트

```python
class Decision(BaseModel):
    next: Literal["calc_agent", "travel_agent", "FINISH"]
    task: str                       # 하위 에이전트에게 줄 작업 지시 (FINISH면 최종 답변)

def supervisor(state) -> Command[Literal["calc_agent", "travel_agent", "__end__"]]:
    steps = state.get("steps", 0) + 1
    if steps > MAX_STEPS:                                   # 안전장치
        return Command(goto=END, update={...})
    d = supervisor_llm.invoke([SystemMessage(SUPERVISOR_PROMPT)] + state["messages"])
    if d.next == "FINISH":
        return Command(goto=END, update={"messages": [AIMessage(d.task, name="supervisor")]})
    return Command(goto=d.next, update={"task": d.task, "steps": steps})

def make_worker(name, agent):                               # create_agent로 만든 하위 에이전트를 감싸는 노드
    def worker(state) -> Command[Literal["supervisor"]]:
        result = agent.invoke({"messages": [HumanMessage(state["task"])]})   # 작업 지시만 전달 (컨텍스트 격리)
        return Command(goto="supervisor", update={"messages": [AIMessage(result["messages"][-1].text, name=name)]})
    return worker
```

- 그래프에는 `START → supervisor` 엣지 하나만 그렸다. 나머지 이동은 반환 타입 `Command[Literal[...]]`이 정한다(그림에 점선으로 나온다).
- 요청 "3일 × 하루 식비 45,000원 + 서울 날씨"
  - 감독자 #1 → calc_agent. 그런데 **작업 지시 안에 "총 식비는 135,000원입니다"라고 이미 계산해서** 보냈다. 계산 도구가 있는 하위 에이전트를 두고도 감독자 LLM이 직접 계산한 것이다(이번엔 맞았지만 검증되지 않은 값).
  - 감독자 #2 → travel_agent(맑음 18°C) → #3 FINISH로 종합.
- `show_graph(supervisor_app, xray=True)`로 그리면 하위 에이전트 안의 `model ↔ tools` 루프까지 보인다.

## 예제 ④ 다관점 병렬 리뷰: Map-Reduce (`Send`)

```python
class ReviewState(TypedDict):
    idea: str
    perspectives: list[str]
    reviews: Annotated[list[str], operator.add]   # 병렬 결과를 모으는 리듀서

def dispatch(state):
    return [Send("reviewer", {"idea": state["idea"], "perspective": p, "index": i})
            for i, p in enumerate(state["perspectives"])]   # 관점 수만큼 reviewer를 동시에 실행
```

- 기획자(gpt)가 관점 4개(기술·시장·사용자 경험·비즈니스 모델)를 정하고, 리뷰어를 gpt/gemini에 번갈아 배정했다. **4건 동시 실행에 6.0초**.
- 완료 순서는 gemini, gemini, gpt, gpt로 **요청 순서와 달랐다**. 병렬 결과는 끝난 순서대로 쌓이므로 순서가 중요하면 `index`로 다시 정렬한다.
- `operator.add`를 빼면 여러 노드가 같은 단계에서 한 키를 갱신해 `InvalidUpdateError`가 난다.
- `Send`: 특정 노드에 **별도 입력**을 주며 실행(같은 노드를 여러 입력으로 여러 번). `Command`: 현재 노드에서 **State 갱신 + 다음 이동**을 함께.

## 예제 ⑤ 작성자·비평가 자기 개선 루프 + 사람 승인 (HITL)

```python
def after_critic(state) -> str:
    if state["score"] >= PASS_SCORE or state["revisions"] >= MAX_REVISIONS:
        return "human_review"
    return "writer"

def human_review(state) -> Command[Literal["writer", "__end__"]]:
    answer = interrupt({"질문": "승인하려면 'ok', 아니면 수정 의견", "문구": state["draft"], "AI 점수": state["score"]})
    if answer.strip().lower() == "ok":
        return Command(goto=END, update={"approved": True})
    return Command(goto="writer", update={"feedback": f"[사람 의견] {answer}", "revisions": 0})

copy_app = builder.compile(checkpointer=InMemorySaver())   # interrupt는 체크포인터가 있어야 멈췄다 이어진다
```

실행 흐름(제품: "한 번 충전으로 일주일 쓰는 초경량 무선 마우스", `PASS_SCORE=8`, `MAX_REVISIONS=3`):

| 단계 | 결과 |
|---|---|
| 자동 루프 | 7점 → 수정 → 8점 통과 → `human_review`에서 멈춤 |
| 사람 의견 "대학생 타깃이 드러나게, 가격 대비 장점을 한 문장 넣어줘" | `revisions`를 0으로 되돌리고 writer로 → 7, 7, 7점 → 상한 도달로 다시 사람에게 |
| 사람 "ok" | 승인, `approved=True` |
| `get_state_history()` | 스냅숏 14개를 거꾸로 확인 |

- 최종 문구에 "**계란 한 판보다 가벼운 50g**"이 들어갔다. 초안의 "계란 하나보다 가벼운"이 수정 중에 바뀐 것인데, 계란 한 판(약 1.8kg)과 비교하면 가볍다는 말이 의미가 없다. 비평가도 사람도 놓쳤다. **점수가 아니라 사실 관계를 확인하는 검토 기준**이 필요하다.
- 사람 피드백 뒤 점수가 7점에서 오르지 않았다. 비평가(gpt)의 기준과 사람의 요구가 다르면 자동 루프는 상한까지 돌기만 한다.
- 멈춘 노드는 **재개될 때 처음부터 다시 실행**된다(10/23에 확인). `interrupt()` 앞에는 다시 실행돼도 되는 코드만 둔다.

## 정리: `create_agent` + 미들웨어 vs LangGraph

미들웨어 훅이 갈 수 있는 곳(`JumpTo`)은 `('tools', 'model', 'end')` 세 곳뿐이다.

```python
middleware_agent = create_agent(model=gpt, tools=[flaky_multiply], middleware=[
    ModelCallLimitMiddleware(run_limit=3, exit_behavior="end"),   # LLM 판단 최대 3번
    ToolCallLimitMiddleware(run_limit=2, exit_behavior="end"),    # 도구 요청 최대 2건
    ToolRetryMiddleware(max_retries=3, initial_delay=0.3),        # 요청 1건당 최초 1번 + 재시도 3번
])
```

- 3번 중 2번 실패하는 곱셈 도구로 "153 곱하기 27은?"을 물었더니 `Tool call limit reached: run limit exceeded (3/2 calls).`만 남기고 **답 없이 끝났다**. 재시도를 다 써도 실패하면 오류가 모델에 전달되고, 모델이 도구를 다시 요청하다 호출 한도에 걸린 것이다. `exit_behavior="end"`는 안전하게 멈추지만 사용자에게 줄 답은 따로 만들어야 한다.
- 그래프를 그리면 `ModelCallLimitMiddleware.before_model` 같은 **훅 노드**가 model 앞뒤에 끼어든다.

| 기능 | 미들웨어로 되는 범위 | LangGraph가 필요해지는 경우 |
|---|---|---|
| 분기 | `jump_to`로 tools / model / end | 전문가 노드 여러 개로 나누기 (라우터·감독자) |
| 병렬 | 한 번에 여러 도구 호출 | 관점별 리뷰어를 동적으로 여러 개 (`Send`) |
| 반복 | 모델 ↔ 도구 루프 | 작성자 ↔ 비평가처럼 에이전트 사이 루프 |
| 사람 승인 | `HumanInTheLoopMiddleware`(도구 호출 승인) | 임의 단계에서 멈추고 의견 받아 되돌리기 |

## 🔁 복습 질문

<details>
<summary>1. 감독자 패턴에서 그래프 엣지를 거의 그리지 않아도 되는 이유는?</summary>

노드 함수가 `Command(goto=..., update=...)`를 반환해 다음 목적지를 직접 정하기 때문이다. 반환 타입 `Command[Literal[...]]`을 적어야 그래프 그림과 검증에 목적지가 나타난다.
</details>

<details>
<summary>2. <code>Send</code>로 병렬 실행한 결과를 한 리스트에 모으려면 State에 무엇이 필요한가?</summary>

`Annotated[list[str], operator.add]` 같은 리듀서. 없으면 같은 슈퍼스텝에서 여러 노드가 한 키를 갱신해 오류가 난다.
</details>

<details>
<summary>3. 하위 에이전트에게 전체 대화 대신 작업 지시만 넘기는 이유는?</summary>

컨텍스트 격리. 필요한 정보만 받아야 프롬프트가 짧고 결과가 안정적이며, 감독자 대화에는 하위 에이전트의 최종 보고만 남는다.
</details>

<details>
<summary>4. 사람 의견을 받은 뒤 <code>revisions</code>를 0으로 되돌린 이유와 그 부작용은?</summary>

사람이 요청한 수정에 다시 자동 개선 기회를 주기 위해서다. 대신 비평가가 계속 기준 미달을 주면 상한까지 LLM 호출이 반복된다(이번 실행: 7, 7, 7).
</details>

<details>
<summary>5. 미들웨어 에이전트가 "Tool call limit reached"로 끝났을 때 사용자에게 무엇을 보여 줘야 하나?</summary>

호출 한도 메시지는 사용자용 답이 아니다. 종료 이유를 확인해 "계산 도구가 응답하지 않아 결과를 확인하지 못했다" 같은 대체 답을 코드에서 만들어 준다.
</details>
