# AI 에이전트 이론: 챗봇과 에이전트, 하네스, 설계 과정, 오케스트레이션 패턴

> **한눈에 보기**
> - **챗봇**은 질문에 한 번 답하는 시스템, **에이전트**는 목표를 위해 스스로 계획하고 도구를 쓰고 결과를 확인하며 반복하는 시스템
> - **하네스(harness)**: 모델을 에이전트로 "실제로 움직이게" 하는 실행 골격 — 목표, 프롬프트, 상태·메모리, 계획, 도구, 실행 루프, 안전장치(HITL), 평가·로깅
> - 에이전트 설계 8단계: 문제 정의 → 에이전트가 필요한지 판단 → 데이터 → 모델·도구 → 워크플로 → 안전장치 → 구현·평가 → 배포·운영
> - LangChain `create_agent()`는 빠르게, LangGraph `StateGraph`는 흐름을 직접 설계. `create_agent()`도 내부는 LangGraph로 동작한다
> - LangGraph 오케스트레이션 4패턴: **순차 / 슈퍼바이저 / 상호 협업(루프) / 계층형(서브그래프)**

## 1. 챗봇 vs 에이전트

| 구분 | 챗봇 (대화형 응답 시스템) | 에이전트 (작업 수행형 AI) |
|---|---|---|
| 목표 | 질문에 답변 | 목표 달성과 작업 완료 |
| 동작 방식 | 1회 응답 중심 | 계획 → 실행 → 관찰 → 수정 (반복) |
| 도구 사용 | 선택적, 단순한 도구만 | 적극적으로 도구·API·DB 사용 |
| 상태 관리 | 대화 컨텍스트 안에서만 | 상태·메모리를 지속적으로 관리 |
| 반복 실행 | 거의 없음 | 결과를 보고 반복·개선 |
| 적합한 일 | FAQ, 설명, 요약, 초안 작성 | 조사, 리서치, 데이터 분석, 여러 단계 업무 자동화 |
| 장점 | 빠르고 간단하고 비용·지연이 적다 | 복잡한 업무를 자율적으로 수행 |
| 주의점 | 복잡한 업무에는 부족 | 구성이 복잡하고 안전장치가 필요 |

언제 무엇을 쓸까: 빠른 질의응답·요약·FAQ처럼 **한 번에 답이 나오는 일**은 챗봇으로 충분하다. 여러 단계와 외부 도구(API·DB·웹)가 필요하고 **결과를 확인하며 반복해야 하는 일**에 에이전트를 쓴다.

> 한 줄 요약: 챗봇은 "잘 대답하는 AI", 에이전트는 "목표를 향해 도구를 써서 일하는 AI", 하네스는 그 에이전트를 **안전하고 반복 가능하게** 움직이는 운영 골격이다.

## 2. 에이전트 하네스(harness)

모델(LLM)만으로는 부족하다. 하네스는 프롬프트, 상태, 도구, 실행 흐름, 안전장치, 평가를 묶어 에이전트가 안정적으로 동작하게 하는 **실행 골격·운영 틀**이다.

| 구성 요소 | 하는 일 | 이 과정에서 본 예 |
|---|---|---|
| Goal & Role | 목표, 역할, 성공 기준 | 시스템 프롬프트의 역할 지정 |
| Prompt / Policy | 지시, 규칙, 출력 형식 | "문서에 없으면 모른다고 답하라" ([9/28](../ex0928/RAG실습.md)) |
| State / Memory | 대화·작업 상태, 장기 기억 | LangGraph 상태, `MessagesState` ([10/01](../ex1001/랭그래프기본개념.md)) |
| Planner / Router | 계획 수립, 다음 단계 선택 | 조건부 엣지, 라우팅 함수 |
| Tools / APIs / DB | 실제 행동 | 검색, 날씨, 계산기, 벡터 DB |
| Execution Loop | Plan → Act → Observe → Revise | ReAct 루프 ([10/16](../ex1016/다중LLM과ReAct.md)) |
| Guardrails / HITL | 권한, 금지 행동, 사람 승인 | 가드레일 노드, 주문 전 사람 승인 |
| Evaluation / Logging | 품질 평가, 로그, 트레이싱 | LangSmith, 환각 평가 노드 |

하네스 진행 8단계: ① 사용자 요청 수신 → ② 목표 해석 → ③ 상태 확인 → ④ 계획 수립 → ⑤ 도구 호출·작업 수행 → ⑥ 결과 관찰 → ⑦ 필요 시 수정·반복 → ⑧ 최종 응답 및 로그 저장

## 3. AI 에이전트 설계 과정 8단계

| 단계 | 할 일 | 스스로 물어볼 것 |
|---|---|---|
| 1. 문제 정의 | 해결할 업무와 사용자, 입력·출력·성공 기준(KPI), 비용·시간·정확도 제약 | 누구를 위해 어떤 문제를 푸는가? |
| 2. 에이전트가 필요한지 판단 | 단순 질의응답이면 챗봇으로 충분. 여러 단계 판단·도구 사용이 필요한가? 사람이 승인할 행동이 있는가? | 정말 에이전트여야 하는가? |
| 3. 지식과 데이터 준비 | 문서, DB, API, 웹, 사내 지식 / RAG·메모리·상태 설계 / 최신성·권한·품질 점검 | 믿을 수 있는 데이터인가? |
| 4. 모델과 도구 선택 | LLM 선택(성능·비용·속도), 검색·계산·코드 실행 도구, Tool schema·timeout·retry | 목적에 맞는 조합인가? |
| 5. 워크플로 설계 | Plan → Act → Observe → Reflect, 상태 전이·분기·루프·종료 조건, 단일 vs 멀티 에이전트 | 언제 끝나는가? |
| 6. 안전장치와 통제 | 권한 범위, 예산 한도, rate limit, 프롬프트 인젝션·환각 대응, HITL 승인 단계 | 잘못 움직이면 무엇이 막는가? |
| 7. 구현과 평가 | 프롬프트·도구 래퍼·메모리 구현, 테스트셋 기반 성공률·지연·비용 평가, 로그·실패 사례 분석 | 숫자로 확인했는가? |
| 8. 배포와 운영 | API·UI 연결, 모니터링·알림, 버전 관리·롤백·관측성, 사용자 피드백으로 개선 | 계속 고칠 수 있는가? |

추가로 고려할 것: **정확도**(정답률, 근거 제시), **비용**(모델·토큰·도구 호출 비용), **속도**(응답 시간, 병렬 처리, 캐싱), **보안**(개인정보, 권한, 외부 API 위험), **운영성**(로그, 장애 대응), **확장성**(사용자·기능 증가).

> 좋은 AI 에이전트 = **명확한 목표** + **믿을 수 있는 도구** + **안전한 흐름** + **꾸준한 평가**

예시로 든 고객지원 에이전트: 문의 이해 → 사내 FAQ·정책 문서 검색(RAG) → 답변 작성 → **환불처럼 민감한 작업은 사람이 승인**. 단순 답변은 자동으로, 민감한 작업은 사람과 함께.

## 4. LangChain vs LangGraph

둘은 별개가 아니라 **계층 관계**다. LangChain의 `create_agent()`는 내부적으로 LangGraph를 사용하고, 둘 다 LangGraph Runtime(상태 관리, 그래프 실행, 체크포인트, 메모리, 스트리밍, 사람 개입) 위에서 돈다.

| 항목 | LangChain (`create_agent`) | LangGraph (`StateGraph`) |
|---|---|---|
| 추상화 수준 | 높음 (간단한 API) | 낮음 (세밀한 제어) |
| 개발 난이도 | 쉬움 | 중간 이상 |
| 적합한 일 | 표준 도구 호출, 간단한 RAG·챗봇 | 복잡한 분기, 반복, 다중 에이전트 |
| 워크플로 | 내부 ReAct 루프에 맡김 | 노드·엣지로 직접 설계 |
| 상태·메모리 | 기본 제공 | 직접 정의하고 세밀하게 관리 |
| 사람 개입(HITL) | 미들웨어로 가능 | `interrupt` 등으로 세밀하게 |

구현 단계 비교

- LangChain: ① 모델 정의(`ChatOpenAI`) → ② `@tool`로 도구 정의 → ③ `create_agent(model, tools, system_prompt)` → ④ `invoke` / `stream`
- LangGraph: ① 상태 정의(`MessagesState` 또는 `TypedDict`) → ② 노드 함수(에이전트·도구) → ③ `StateGraph` 생성 → ④ `add_node`, `add_edge`, `add_conditional_edges` → ⑤ `compile()` → ⑥ `invoke` / `stream`

선택 가이드: 표준적인 도구 호출과 빠른 프로토타입은 **LangChain**, 복잡한 분기·반복·다중 에이전트·세밀한 상태 관리는 **LangGraph**. 처음에는 LangChain으로 빠르게 시작하고, 필요한 부분만 LangGraph로 옮기는 방식도 좋다.

> 한 줄 요약: LangChain은 에이전트를 쉽게 만들고, LangGraph는 실행 과정을 직접 설계한다. ([6.4 create_agent 미들웨어](../ex1008/create_agent미들웨어.md)에서 `create_agent` 결과가 LangGraph 그래프인 것을 이미 봤다)

## 5. 다중 에이전트 설계

**다중 에이전트**: 여러 에이전트가 역할을 나눠 협력하며 하나의 복잡한 목표를 수행하는 구조. 각 에이전트는 서로 다른 전문성, 도구, 기억, 판단 로직을 가질 수 있다. 예: Supervisor/Planner가 요청을 해석해 Research(조사)·Tool(도구 실행)·Writer(초안)·Reviewer(검토) 에이전트에 일을 나눠 준다.

언제 적합한가: 작업이 복잡하고 단계가 많을 때, 역할을 나누면 성능이 좋아질 때, 검토·수정·승인 루프가 필요할 때, 도구 사용과 장기 실행이 많을 때.

설계 8단계

1. **목표와 범위 정의**: 무엇을 해결하나, 최종 산출물, 왜 단일 에이전트가 아닌가, 성공 기준
2. **업무 분해**: 큰 목표를 하위 작업으로, 의존 관계·순서, 병렬 가능한 작업, 반복·검토 단계
3. **에이전트 역할 설계**: Planner/Supervisor, Retriever/Researcher, Coder/Tool User, Writer/Reviewer — 필요한 역할만 최소로 (역할이 많을수록 관리 비용 증가)
4. **상태·메모리·공유 정보 설계**: 공유 state, 단기 기억(checkpoint)과 장기 기억(store) 분리, 권한에 따른 정보 분리
5. **통신과 오케스트레이션 설계**: 누가 누구에게 지시하나, 순차·라우팅·협업 루프·계층 구조, handoff·routing·feedback loop, 사람 승인 필요 여부
6. **도구와 외부 시스템 연결**: 검색, RAG, 벡터 DB, API, 코드 실행, 업무 시스템, 도구 실패 시 fallback
7. **안전장치와 품질 통제**: 권한 관리, 금지 작업, 환각 대응, 검토자 에이전트나 규칙 기반 검증, 예산·시간·반복 횟수 제한
8. **평가·배포·운영**: 테스트 시나리오, 정확도·비용·지연·성공률 측정, 로그·트레이스·관측성, 배포 후 지속 모니터링

설계 체크리스트: 역할이 명확한가? 상태 공유 범위가 정의됐나? 에이전트 간 통신 규칙이 있나? 도구 실패에 대비했나? 평가 기준이 있나? 운영 로그를 볼 수 있나?

> 핵심: 먼저 목표와 분업 이유를 명확히 → 역할·상태·통신 구조 설계 → 도구·안전장치·평가 체계 → **작게 시작해서 반복 개선**

## 6. LangGraph 오케스트레이션 4가지 패턴

오케스트레이션 = 여러 노드(에이전트, 도구, 처리 로직)를 어떻게 연결하고, 상태를 어떻게 흐르게 하고, 다음 단계로 어떻게 라우팅하고, 반복·승인·분기를 어떻게 제어할지 설계하는 것. LangGraph는 이것을 **State(상태) + Nodes(노드) + Edges(엣지)** 로 표현한다.

| 패턴 | 구조 | 언제 쓰나 | 핵심 API | 주의 |
|---|---|---|---|---|
| 1. 순차형 (Pipeline) | START → 수집 → 처리 → 검토 → END | 단계가 고정된 처리, ETL, 보고서 생성 | `add_node`, `add_edge` | 분기·예외 처리에 약함 |
| 2. 슈퍼바이저형 (Router) | 중앙 슈퍼바이저가 상태를 보고 전문 노드(검색·코딩·요약) 선택 | 요청 유형에 따라 처리 경로가 다를 때 | `add_conditional_edges`, `MessagesState`, `ToolNode`, `interrupt` | 슈퍼바이저 설계가 중요, 잘못 라우팅하면 품질 저하 |
| 3. 상호 협업·피드백 루프형 | Planner → Solver → Critic → (충분하면 END, 아니면 다시) | 초안을 검토·수정해 품질을 높일 때 | `add_conditional_edges`, reducer(`add_messages`), `checkpointer`, `interrupt` | **무한 루프 방지 조건 필수**, 비용·지연 증가 |
| 4. 계층형 (Sub-graph) | 상위 매니저 그래프 아래 팀별 서브그래프 | 큰 시스템을 모듈로 나눌 때 | `compile()`, 서브그래프를 노드로 `add_node("team_a", team_a)`, `checkpointer`·`store` | 상태 인터페이스 설계가 어렵고, 부모·자식 디버깅이 복잡 |

슈퍼바이저 라우터 예(의사 코드):

```python
def route(state):
    return "search" if state["query_type"] == "web" else "summarize"
builder.add_conditional_edges("supervisor", route)
```

피드백 루프 종료 조건 예(의사 코드):

```python
def should_continue(state):
    return "planner" if state["need_revision"] else END
builder.add_conditional_edges("critic", should_continue)
```

이 과정에서 만든 것과 연결해 보면: 9/28의 RAG는 **순차형**, 10/08의 [RAG 에이전트](../ex1008/RAG에이전트그래프.md)는 검색 평가 → 질문 재작성 → 재검색을 도는 **피드백 루프형**(그래서 횟수 상한이 필요했다), 10/16 [순차 다중 LLM 파이프라인](../ex1016/다중LLM과ReAct.md)(설계 → 구현 → 검증)은 **순차형** 다중 에이전트다.

<details>
<summary>2. 하네스(harness)는 무엇이고, 왜 모델만으로는 부족한가?</summary>

모델이 에이전트로 안정적으로 움직이게 하는 실행 골격(목표·프롬프트·상태·도구·루프·안전장치·평가)이다. 모델은 다음 말을 생성할 뿐, 도구 실행·상태 저장·반복 제어·승인·로그는 하네스가 맡는다.
</details>

<details>
<summary>3. 설계 2단계 "에이전트가 필요한지 판단"에서 챗봇으로 충분한 경우는?</summary>

한 번의 답으로 끝나는 질의응답·요약·FAQ처럼 여러 단계 판단이나 외부 도구 실행이 필요 없는 경우.
</details>

<details>
<summary>4. <code>create_agent()</code>와 LangGraph는 어떤 관계인가?</summary>

`create_agent()`는 LangGraph로 ReAct 루프 그래프를 만들어 주는 고수준 함수다. 그래서 결과가 `CompiledStateGraph`이고, 더 세밀한 흐름이 필요하면 `StateGraph`로 직접 설계한다.
</details>

<details>
<summary>5. 다중 에이전트에서 역할을 "필요한 만큼만 최소로" 만드는 이유는?</summary>

에이전트가 늘수록 통신·상태 공유·디버깅·비용이 함께 늘어난다. 분업으로 얻는 품질 향상이 그 관리 비용보다 클 때만 나눈다.
</details>

<details>
<summary>6. 피드백 루프형 패턴에서 꼭 넣어야 하는 것은?</summary>

종료 조건(충분하면 END)과 최대 반복 횟수. 없으면 비평과 수정이 끝없이 반복된다 (10/08 RAG 에이전트의 `GraphRecursionError`).
</details>

<details>
<summary>7. 요청 종류에 따라 검색·코딩·요약 노드 중 하나로 보내려면 어떤 패턴과 API를 쓰나?</summary>

슈퍼바이저(라우터)형. 라우팅 함수가 상태를 보고 다음 노드 이름을 반환하고, `add_conditional_edges`로 연결한다.
</details>
