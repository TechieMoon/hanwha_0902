# 임베딩과 벡터 DB (pgvector)

RAG의 바탕이 되는 **임베딩**과 **벡터 DB**를 배웠다. 강의 교안으로 개념을 익히고, 로컬 도커로 띄운 **pgvector**(PostgreSQL에 벡터 기능을 더한 확장)에 OpenAI 임베딩을 저장한 뒤 SQL로 유사도 검색을 해 봤다. 두 문장의 유사도를 돌려주는 FastAPI 서버도 만들었다.

- 코드: [`exam3.ipynb`](exam3.ipynb) (앞부분, mydoc1 실험), [`fastapiedu/exam20.py`](fastapiedu/exam20.py)
- 강의 교안(PDF)은 강사님 자료라 저장소에 넣지 않고 내용만 정리했다.
- 실습 환경: 도커 `ankane/pgvector` (PostgreSQL 15.4, pgvector 0.5.1), OpenAI `text-embedding-3-small`. 노트북에 남은 결과와 함께, 10/16에 같은 DB로 서버 코드를 다시 실행한 결과(exam20)를 넣었다.

## 1. 임베딩이란

임베딩은 텍스트의 **의미**를 고정 길이의 숫자 배열(벡터)로 바꾸는 것이다. 교안에서는 RGB 색상으로 설명했다. 빨강 `(255, 0, 0)`과 주황 `(255, 165, 0)`은 숫자가 비슷하고 색도 비슷하다. 텍스트 임베딩도 같은 원리로, 뜻이 비슷한 문장은 가까운 벡터가 되도록 학습된다. 다만 색은 숫자 3개, OpenAI `text-embedding-3-small`은 숫자 **1,536개**다.

컴퓨터는 글자를 직접 비교할 수 없지만 숫자는 계산할 수 있다. 텍스트를 벡터로 바꾸면 유사도 계산, 단어가 달라도 뜻으로 찾는 의미 검색, 비슷한 글끼리 묶는 분류, 다른 언어끼리의 연결이 가능해진다.

**표현 방식의 발전**

| 단계 | 방식 | 한계 / 특징 |
|---|---|---|
| 1 | 원-핫 인코딩 | 단어마다 자리 하나에 1. 단어 사이 관계를 전혀 모름 |
| 2 | Word2Vec, GloVe | 비슷한 단어를 가까이 배치. 왕 − 남자 + 여자 ≈ 여왕 같은 연산 가능. 동음이의어(배)는 구분 못 함 |
| 3 | ELMo, BERT | 주변 문맥을 보고 같은 단어도 다른 벡터로 표현 (트랜스포머) |
| 4 | LLM 기반 임베딩 (OpenAI 등) | 문장·문서 전체의 의도까지 압축. "돈 빌리는 법"으로 "대출 절차" 문서를 찾음 |

**변환 흐름:** 텍스트 → 토큰으로 자르기 → 토큰 ID → 트랜스포머가 문맥 분석 → 문장 전체를 1,536개 숫자로 압축. 토큰은 단어보다 작을 수 있고(`running` → `run`, `ning`), OpenAI 과금 기준이기도 하다.

## 2. 코사인 유사도

두 벡터가 가리키는 **방향이 얼마나 같은지**로 유사도를 잰다.

```
cosine_similarity(A, B) = (A · B) / (|A| × |B|)
```

교안 예시: `A = [1, 2]`, `B = [2, 4]`이면 내적 10, 길이 √5와 √20이라 10 / 10 = **1.0**. 크기는 달라도 방향이 같아서 완전히 같다고 본다. 수학적으로는 −1 ~ 1이지만 텍스트 임베딩에서는 대부분 0 ~ 1 사이에 나온다.

```python
# exam20.py: 두 문장을 한 번에 임베딩하고 직접 코사인 유사도를 계산
response = client.embeddings.create(model="text-embedding-3-small", input=[request.textA, request.textB])
score = cosine_similarity(response.data[0].embedding, response.data[1].embedding)
```

`POST /api/similarity`에 `{"textA": ..., "textB": ...}`를 보내면 유사도, 백분율, 해석, 걸린 시간을 돌려준다.

실제로 실행해 본 결과:

| textA | textB | 코사인 유사도 | exam20의 해석 |
|---|---|---|---|
| 강아지가 공원에서 뛰어논다. | (같은 문장) | 1.0 | 거의 동일한 의미 |
| 강아지 | 반려견 | **0.2578** | 유사도가 낮음 |
| 강아지 | 자동차 | **0.2843** | 유사도가 낮음 |
| 오늘 점심 뭐 먹지? | 점심 메뉴 좀 추천해 줘 | 0.3933 | 유사도가 낮음 |
| FastAPI는 파이썬 웹 프레임워크입니다. | 주식 시장이 크게 하락했다. | 0.0864 | 유사도가 낮음 |

- **단어 하나끼리 비교하면 믿기 어렵다.** 교안 표에서는 "강아지 vs 반려견"을 0.9 이상의 '매우 유사'로 예시했지만, 실제로는 0.26으로 오히려 "강아지 vs 자동차"(0.28)보다 낮았다. 10/12 실습에서도 '강아지'와 '개'보다 '고양이'의 유사도가 더 높게 나왔다. 단어 하나는 문맥이 없어서 임베딩이 의미를 잘 담지 못한다.
- 뜻이 거의 같은 두 문장(점심 질문)도 0.39였고, 같은 문장 외에는 모두 '유사도가 낮음'으로 분류됐다. exam20의 해석 기준(0.6 / 0.8 / 0.95)은 이 모델의 값 범위와 맞지 않는다.
- 응답 시간은 한 번에 160 ~ 200ms 정도였다(임베딩 API 호출이 대부분).

## 3. 벡터 DB

벡터 DB는 데이터를 임베딩으로 바꿔 저장하고, "단어가 같은가"가 아니라 **"뜻이 가까운가"**로 찾는 DB다. 기존 DB의 `LIKE '%스티커%'`는 그 글자가 있어야 찾지만, 벡터 DB는 "다이어리 꾸미기 소품 수집"으로 물어도 "스티커 모으기"를 찾는다. LLM이 모르는 최신·내부 정보를 찾아 주는 **외부 기억 장치**로 RAG에 쓰인다.

교안에서 비교한 벡터 DB들을 정리하면:

| 종류 | 예 | 언제 쓰나 |
|---|---|---|
| 완전 관리형 클라우드 | Pinecone | 운영 부담 없이 대규모 서비스 |
| 오픈소스 전용 DB | Weaviate, Qdrant, Milvus | 필터링·멀티모달·초대규모 분산 등 기능이 필요할 때 |
| 가벼운 개발용 | Chroma | 프로토타입, 소규모 RAG (책 실습 6.5절에서 사용) |
| 기존 DB 확장 | **pgvector**(PostgreSQL), Redis, Elasticsearch | 이미 쓰는 DB에 벡터 검색을 더할 때. SQL·키워드 검색과 함께 사용 |

## 4. pgvector

`CREATE EXTENSION IF NOT EXISTS vector;`를 실행하면 PostgreSQL에 `vector` 타입, 거리 연산자, 벡터 전용 인덱스가 생긴다. 익숙한 `SELECT`, `INSERT`로 벡터를 다룰 수 있다는 게 장점이다.

```bash
docker volume create vpg
docker run -p 5432:5432 -d -e POSTGRES_USER=edu -e POSTGRES_PASSWORD=1234 -e POSTGRES_DB=edudb \
  -v vpg:/var/lib/postgresql/data --name edupgvector ankane/pgvector
docker start edupgvector   # 다음부터는 이것만
```

| 연산자 | 의미 | 값의 뜻 |
|---|---|---|
| `<=>` | 코사인 **거리** | 0에 가까울수록 비슷함. 유사도 = `1 - 거리` |
| `<->` | 유클리드(L2) 거리 | 작을수록 비슷함 |
| `<#>` | 음수 내적 | 작을수록 비슷함 (정규화된 벡터에서는 코사인과 같은 순서) |

- **거리와 유사도를 구분한다.** 교안 표에는 `<=>`가 "코사인 유사도"로 적혀 있지만 실제로 돌려주는 값은 **거리**다. 노트북에서 `embedding <=> 질문`과 `1 - (embedding <=> 질문)`을 같이 출력해 보니 모든 행에서 두 값의 합이 1이었다.
- **정렬은 거리로**: `ORDER BY embedding <=> %s::vector LIMIT k`가 인덱스를 쓰는 기본 형태다.
- **형 맞추기**: 파이썬 리스트를 넘길 때는 `%s::vector`로 캐스팅하거나 `register_vector(conn)` 후 `Vector`/리스트를 넘긴다.
- **인덱스**: 데이터가 수십만 건 이상이면 ANN 인덱스(HNSW: 계층형 그래프, IVFFlat: 클러스터 기반)가 필요하다. 사용하는 연산자에 맞는 인덱스(`vector_cosine_ops` 등)를 만들어야 한다.

## 5. 실습: mydoc1에 6문장 저장하고 검색

AX, FastAPI, Docker Compose, 임베딩 모델, RAG, 강사님 소개(별명·좋아하는 음식·사는 곳) 6문장을 임베딩해서 `mydoc1` 테이블에 저장했다.

```sql
SELECT content,
       embedding <=> %s::vector AS distance,
       1 - (embedding <=> %s::vector) AS similarity
FROM mydoc1
ORDER BY distance;
```

| 검색어 | 1위 (유사도) | 2위 (유사도) | 확인한 점 |
|---|---|---|---|
| "별명" | 강사님 소개 | RAG | "오뎅"과 TOP3 순서가 똑같음 |
| "오뎅" | 강사님 소개 (0.164) | RAG (0.143) | 떡볶이(분식)와 의미가 이어져 1위지만 2위와 차이가 거의 없음 |
| "집" | 강사님 소개 (0.204) | Docker Compose (0.153) | "~에서 살고 있습니다"를 '사는 곳'으로 연결 |
| "OOO강사는 어떤 음식을 좋아할까?" | 강사님 소개 (**0.546**) | RAG (0.078) | 질문이 문장이면 정답과 나머지의 차이가 뚜렷함 |

배운 점:

- **`LIMIT k`는 관련이 없어도 항상 k개를 돌려준다.** "별명"과 "오뎅"처럼 상관없는 검색어도 같은 3개가 나왔다. 엉뚱한 문서를 근거로 쓰지 않으려면 유사도 임계값(`WHERE 1 - 거리 >= 기준`)이 필요하다.
- **실제 유사도 값은 교안 해석표보다 훨씬 낮다.** 교안은 0.9 이상을 '매우 유사', 0.4 미만을 '거의 관련 없음'으로 설명하고 exam20도 0.6 미만을 '유사도가 낮음'으로 해석한다. 하지만 이 실험에서는 정답 문장도 0.546이었고 관련 없는 문장은 0.02 ~ 0.2였다. 임계값은 표를 그대로 쓰지 말고 **내 데이터로 값을 확인한 뒤** 정해야 한다.
- 단어 하나보다 질문 문장으로 검색할 때 정답이 더 확실히 구분됐다. (위 exam20 결과처럼 단어끼리의 유사도는 순서조차 믿기 어려웠다)

## 6. 임베딩 모델 고르기

| 상황 | 교안 추천 |
|---|---|
| 처음 시작 | `text-embedding-3-small` (1536차원, 빠르고 저렴) |
| 품질이 가장 중요 | `text-embedding-3-large` (3072차원) |
| 한국어 문서 위주 | `multilingual-e5-large` 같은 다국어 모델 |
| 비용 절감, 로컬 실행 | `BGE-M3` 같은 오픈소스 모델 |

어떤 모델이든 **저장할 때와 검색할 때 같은 모델**을 써야 한다. 모델이 다르면 벡터 공간이 달라서 거리가 의미 없어진다. (책 실습에서 Chroma DB를 다시 불러올 때도 같은 이유로 같은 모델을 지정했다)

## 정리

| 개념 | 핵심 |
|---|---|
| 임베딩 | 텍스트의 의미 → 숫자 벡터 (`text-embedding-3-small`은 1536개) |
| 코사인 유사도 | 내적 / (길이 × 길이). 방향이 같을수록 1 |
| 벡터 DB | 뜻이 가까운 데이터를 찾는 DB. RAG의 외부 기억 장치 |
| pgvector | PostgreSQL 확장. `vector` 타입, `<=>`(코사인 거리), HNSW·IVFFlat 인덱스 |
| 거리 vs 유사도 | `<=>`는 거리. 유사도 = 1 − 거리, 정렬은 거리 오름차순 |
| 임계값 | `LIMIT`만으로는 관련 없는 문서도 나온다. 실제 데이터의 값을 보고 기준을 정한다 |
