## 1. 사용자 정의 도구 만들기 (6.3.1)

`@tool`로 만든 도구는 LLM에게 **이름, 설명, 인자 스키마** 세 가지로 전달된다. LLM은 코드를 보지 못하고 이 설명서만 보고 도구를 부를지 정한다.

```python
from langchain.tools import tool

# @tool: 함수를 LLM이 호출할 수 있는 도구로 만든다.
@tool
def multiply(a: int, b: int) -> int:
    """Multiply two numbers."""
    return a * b
```

출력 (`name`, `description`, `args`):

```txt
multiply
Multiply two numbers.
{'a': {'title': 'A', 'type': 'integer'}, 'b': {'title': 'B', 'type': 'integer'}}
```

기본 `@tool`은 인자 타입만 알려주고 인자가 무엇인지는 설명하지 않는다. `@tool(parse_docstring=True)`로 만들고 docstring에 `Args:`를 적으면 인자마다 설명이 붙는다.

```txt
multiply
Multiply two numbers.
{'a': {'description': 'The first number.', 'title': 'A', 'type': 'integer'}, 'b': {'description': 'The second number.', 'title': 'B', 'type': 'integer'}}
```

`args_schema.model_json_schema()`로 보면 LLM 요청에 실리는 최종 JSON 스키마(설명, 인자별 타입·설명, 필수 인자)를 확인할 수 있다. 자세한 코드와 출력은 노트북에 있다.

## 2. 코드 실행 도구 (6.3.2)

LLM이 넘긴 코드를 `exec()`로 실제 실행한다. 인자 기본값에 `pydantic.Field(description=...)`를 주는 것도 인자 설명을 붙이는 방법이다. 같은 버전으로 확인해 보면 `python_exec_tool.args`에 `'imports': {'description': '임포트 구문', ...}`, `'code': {'description': '임포트 구문을 제외한 코드 블록', ...}`처럼 설명이 들어간다.

```python
from pydantic import Field 
from langchain.tools import tool 

# 코드 실행 도구 (6.3.2): LLM이 작성한 파이썬 코드를 exec()로 실제 실행한다.
# 인자 기본값으로 pydantic Field(description=...)를 주면, 그 설명이 LLM이 읽는 도구 설명서(args)에 들어간다.
@tool 
def python_exec_tool(
    # import 문만 따로 받는다.
    imports: str = Field(description="임포트 구문"),
    # import 문을 뺀 나머지 코드
    code: str = Field(description="임포트 구문을 제외한 코드 블록"),
) -> str:
    """
    파이썬 코드를 실행하는 도구입니다. 만약 코드 실행에 실패하면 에러 메시지를 반환합니다.
    실행 결과를 확인하고 싶다면 `print(...)`를 사용하여 출력해야 합니다.
    
    Args:
        imports: 임포트 구문 
        code: 임포트 구문을 제외한 코드 블록 
        
    Returns:
        실행 결과 또는 에러 메시지
    """
    # 1단계: import 문만 먼저 실행해서 모듈을 불러올 수 있는지 확인
    # Check imports 
    try:
        exec(imports)
    except Exception as e:
        return f"모듈을 임포트하는 데 실패했습니다. ERROR: {repr(e)}"
    
    # 2단계: import 문 + 코드를 함께 실행. 에러가 나면 에러 메시지를 LLM에게 돌려준다.
    # Check execution 
    try:
        # 주의: 코드 안의 print() 결과는 터미널에 찍힐 뿐, 이 도구의 반환값(LLM이 보는 내용)에는 들어가지 않는다.
        exec(imports + "\n" + code)
    except Exception as e:
        return f"코드 실행에 실패했습니다. ERROR: {repr(e)}"
    
    # 성공하면 실행한 코드를 그대로 돌려준다. (실행 결과가 아니라 '에러 없이 실행됐다'는 사실만 전달)
    result_str = f"성공적으로 코드가 실행되었습니다. :\n```python\n{code}\n```"
    
    return result_str
```

import 문과 나머지 코드를 따로 받아서, import가 실패한 건지 코드가 실패한 건지 구분해서 에러를 돌려준다. 에러 메시지를 받은 LLM은 코드를 고쳐서 다시 실행을 요청할 수 있다.

**이 도구의 한계:** docstring에는 "실행 결과를 확인하고 싶다면 `print(...)`를 사용하라"고 적혀 있지만, `exec()` 안의 `print()`는 터미널에만 찍히고 도구의 반환값에는 들어가지 않는다. 성공했을 때 LLM이 받는 건 "성공적으로 코드가 실행되었습니다"와 실행한 코드뿐이다. 그래서 LLM이 확인할 수 있는 건 **에러 없이 실행됐는지**까지이고, 출력값이 맞는지는 볼 수 없다. 출력까지 돌려주려면 `contextlib.redirect_stdout`으로 print 결과를 문자열로 받아서 반환값에 넣으면 된다.

## 3. 파일 저장 도구 (6.3.3)

LLM이 정한 경로와 내용으로 파일을 저장한다.

```python
# 파일 저장 도구 (6.3.3): LLM이 정한 경로에 내용을 써서 파일로 저장한다.
@tool 
def file_write_tool(
    file_path: str = Field(description="생성/수정할 파일의 경로"),
    content: str = Field(description="파일에 작성할 내용")
) -> str:
    """
    파일을 생성하거나 내용을 작성하는 도구입니다.
    
    Args:
        file_path: 생성/수정할 파일의 경로
        content: 파일에 작성할 내용
        
    Returns:
        성공/실패 메시지
    """
    # 상대 경로면 프로그램을 실행한 폴더(현재 작업 폴더) 기준으로 저장된다.
    try:
        with open(file_path, 'w', encoding="utf-8") as f:
            f.write(content)
        return f"파일 '{file_path}'에 성공적으로 작성했습니다."
    # 실패해도 프로그램을 멈추지 않고, 실패 메시지를 LLM에게 돌려준다.
    except Exception as e:
        return f"파일 작성 실패: {repr(e)}"
```

## 4. create_agent로 에이전트 만들기

6.2에서는 `chatbot` 노드, 도구 실행 노드(`BasicToolNode`), 라우팅 함수, `tools → chatbot` 엣지를 직접 만들었다. `create_agent(llm, tools)`는 이 **"LLM 호출 ↔ 도구 실행" 반복 그래프를 한 번에** 만들어 준다. 노드 이름은 `model`(LLM 호출)과 `tools`(도구 실행)이다.

```python
# [2차 버전] 코드 실행 + 파일 저장 도구를 가진 에이전트 (지금 실행되는 코드)
##################### 코드 생성 및 파일 저장 에이전트 ########################
############################################################################
from dotenv import load_dotenv 

# .env의 OPENAI_API_KEY를 환경변수로 불러온다.
load_dotenv()

# 같은 폴더의 tools.py에서 직접 만든 도구 두 개를 가져온다.
from tools import python_exec_tool, file_write_tool

from langchain.agents import create_agent 
from langchain_openai import ChatOpenAI 

# 에이전트가 쓸 수 있는 도구 목록
tools = [python_exec_tool, file_write_tool]

llm = ChatOpenAI(model="gpt-4o")
# create_agent: 6.2에서 직접 만든 'chatbot ↔ tools 반복 그래프'를 한 줄로 만들어 주는 함수.
# 노드 이름은 model(LLM 호출)과 tools(도구 실행)이다.
graph = create_agent(llm, tools)

if __name__ == "__main__":
    response = graph.stream(
        {
            # 메시지 두 개를 넣으면 HumanMessage 두 개로 들어간다: 코드 작성·실행 확인 요청, 파일 저장 요청
            "messages": [
                "첫 번째 항이 1인 피보나치 수열을 출력하는 파이썬 코드를 작성해주세요. 정상적으로 실행되는지 확인도 해주세요.",
                "확인했다면 그 코드는 .py 파일로 저장하세요."
            ]
        }
    )
    
    # updates 모드: 노드가 끝날 때마다 {노드 이름: 그 노드가 추가한 값}을 받는다.
    for chunk in response:
        for node, value in chunk.items():
            if node:
                print("---", node, "---")
            # 각 노드가 추가한 첫 번째 메시지의 내용만 출력 (도구를 요청하는 model 응답은 content가 비어 있다)
            if "messages" in value:
                print(value["messages"][0].content)
```

파일 위쪽에는 코드 실행 도구만 가진 1차 버전이 주석으로 남아 있다.

실행:

```bash
cd ex1007
uv run coding_agent/agent.py
```

에이전트가 저장한 `fibonacci.py`:

```python
def fibonacci_sequence(n):
    fib_seq = [1, 1]  # Starting with first two terms as 1, 1
    while len(fib_seq) < n:
        fib_seq.append(fib_seq[-1] + fib_seq[-2])
    return fib_seq

# Example usage: Generate first 10 Fibonacci numbers
print(fibonacci_sequence(10))
```

결과를 보면서 확인한 점이 세 가지 있다.

**① 실행 확인과 파일 저장을 동시에 요청했다.** 흐름이 `model → tools → tools → model`이다. 실행 결과를 확인하고 저장하려면 `model → tools(실행) → model → tools(저장) → model`이어야 하는데, 중간에 `model`이 없다. LLM이 첫 응답 하나에 **코드 실행과 파일 저장 도구 호출을 동시에** 넣었다는 뜻이다(병렬 도구 호출). `create_agent`는 요청받은 도구 호출을 각각 실행해서 `tools` 출력이 두 번 찍혔다. 가짜 LLM이 한 응답에 도구 호출 두 개를 담도록 해서 같은 버전으로 재현해 보니 똑같이 `model → tools → tools → model`이 나왔다. 이번에는 코드가 정상이라 문제없었지만, "확인했다면 저장하라"는 조건은 실제로는 지켜지지 않은 셈이다. 순서를 지키게 하려면 시스템 프롬프트로 "실행 결과를 확인한 다음에 저장하라"고 지시하거나, 병렬 도구 호출을 끄는 옵션을 쓰는 방법이 있다.

**② `[1, 1, 2, ...]`가 `--- tools ---`보다 먼저 찍혔다.** 이 줄은 LLM의 답변이 아니라 코드 실행 도구 안에서 `exec()`가 실행한 `print()`의 출력이다. `stream()`은 노드 실행이 **끝난 뒤에** 결과를 넘겨주므로, 도구가 실행되는 동안 찍힌 print가 노드 이름보다 먼저 나온다. 그리고 2에서 본 것처럼 LLM은 이 출력값을 받지 못했다.

**③ 파일은 실행한 위치에 저장된다.** `ex1007` 폴더에서 `uv run coding_agent/agent.py`로 실행했기 때문에, 상대 경로 `fibonacci.py`는 `coding_agent/`가 아니라 실행한 위치인 `ex1007/`에 저장됐다.

## 6. 주의: exec()는 LLM이 만든 코드를 그대로 실행한다

코드 실행 도구는 LLM이 작성한 코드를 **내 컴퓨터에서, 내 권한으로** 실행한다. 파일 삭제나 외부 전송 같은 코드도 그대로 실행될 수 있으므로 실습용으로만 쓰고, 실제 서비스라면 격리된 환경(샌드박스, 컨테이너)에서 실행해야 한다. 파일 저장 도구도 경로 제한이 없어서 어떤 파일이든 덮어쓸 수 있다.

## 정리

| 개념 | 코드 | 핵심 |
|---|---|---|
| 사용자 정의 도구 | `@tool`, `@tool(parse_docstring=True)`, `Field(description=...)` | LLM은 도구의 이름·설명·인자 설명만 보고 판단한다 |
| 코드 실행 도구 | `exec(imports + "\n" + code)` | 실패하면 에러 메시지를 돌려줘서 LLM이 고칠 수 있게 한다. print 결과는 LLM에게 전달되지 않는다 |
| 파일 저장 도구 | `open(file_path, 'w')` | 상대 경로는 실행한 위치 기준 |
| 에이전트 생성 | `create_agent(llm, tools)` | 6.2에서 직접 만든 `model ↔ tools` 반복 그래프를 한 줄로 |
| 병렬 도구 호출 | `model → tools → tools → model` | LLM은 한 응답에 도구 호출을 여러 개 넣을 수 있다. 순서가 중요하면 따로 지시해야 한다 |
