# 구조화된 출력: OpenAI SDK와 Ollama(EXAONE 3.5)

> **한눈에 보기**
> - LLM 답을 DB·API·화면에 바로 쓰려면 "JSON처럼 보이는 글"이 아니라 **스키마에 100% 맞는 데이터**가 필요하다
> - OpenAI: `json_object`(문법만 보장) → `json_schema` strict(필드까지 보장) → **Pydantic + `.parse()`**(권장)
> - 중첩 모델, Enum, `X | None`, `Literal` 판별 필드, refusal 확인, 스트리밍, Function calling으로도 구조화 출력을 받는다
> - Ollama(EXAONE)는 `format=스키마`로 받고 직접 검증한다. 로컬 모델일수록 **검증-재시도**가 필수
> - 구조화 출력은 **형식만** 보장한다. 내용(계산, 분류)이 맞는지는 따로 확인해야 한다

## 1. 왜 필요한가

프롬프트에 "JSON으로 답해줘"라고만 쓰면 이런 일이 생긴다.

- ` ```json ... ``` ` 코드블록으로 감싸서 `json.loads()`가 실패한다
- 필드 이름이 매번 다르다 (`rating` / `score`)
- 필수 필드를 빼먹거나 숫자를 문자열로 준다 (`"rating": "5"`)

## 2. OpenAI에서 구조화 출력을 받는 방법

| Case | 방법 | 보장되는 것 |
|---|---|---|
| A | `response_format={"type": "json_object"}` | 문법상 올바른 JSON. 필드는 프롬프트로 부탁할 뿐 |
| B | `response_format={"type": "json_schema", ..., "strict": True}` (스키마 dict 직접 작성) | 스키마의 필드와 타입 |
| C | `client.beta.chat.completions.parse(response_format=Pydantic모델)` | B와 같음 + `message.parsed`가 바로 Pydantic 객체 (**권장**) |
| J | `openai.pydantic_function_tool(모델)` + `tool_choice`로 함수 호출 강제 | 함수 인자로 구조화 데이터. 다른 도구와 함께 쓰는 에이전트에 자연스럽다 |

strict 모드의 조건: **모든 필드가 `required`**, 모든 객체에 `"additionalProperties": false`. Pydantic을 쓰면 SDK가 알아서 맞춰 준다.

```python
class ReviewExtraction(BaseModel):
    product: str
    rating: int

completion = openai_client.beta.chat.completions.parse(
    model="gpt-4o-mini",
    messages=[...],
    response_format=ReviewExtraction,
)
review = completion.choices[0].message.parsed   # ReviewExtraction(product='노트북', rating=5)
```

## 3. 스키마 설계 도구들

| Case | 상황 | 코드 | 실행 결과 |
|---|---|---|---|
| D | 객체 안에 리스트, 리스트 안에 객체 | `subjects: list[Subject]` | 둘리 3학년, 국어·수학·영어, 평균 84.33 |
| E | 정해진 값 중 하나 (분류) | `class Sentiment(str, Enum)` | 부정 / 중립 / 긍정 리뷰를 정확히 분류 |
| F | 없을 수도 있는 값 | `phone: str \| None = None` | 전화번호 없는 사람은 `phone=None` |
| G | 두 스키마 중 하나 | `MeetingEvent \| VacationEvent` + `Literal["meeting"]` 판별 필드 | 회의 / 휴가로 나뉘어 들어옴 |
| H | 모델이 응답을 거부한 경우 | `.parsed`보다 **`.refusal`을 먼저 확인** | (무해한 리뷰라 거부 없음) |
| I | 긴 응답을 점진적으로 표시 | `beta.chat.completions.stream(...)` → `get_final_completion()` | 토큰이 오다가 마지막에 파싱된 객체 |

- strict 모드에서 `X | None`은 "필드가 없을 수 있다"가 아니라 **"필드는 항상 있고 값이 null일 수 있다"** 는 뜻이다.
- 평균 84.33은 모델이 계산한 값이다. 이번엔 맞았지만((88+95+70)/3), 계산이 필요한 필드는 코드로 다시 계산해 확인하는 게 안전하다.
- `minLength`, `maximum` 같은 제약은 OpenAI 구조화 출력에서 **무시된다**. 길이·범위 규칙은 받은 뒤 Pydantic 검증으로 따로 확인한다.

## 4. 로컬 모델(Ollama, EXAONE 3.5)

| | OpenAI | Ollama |
|---|---|---|
| 스키마 전달 | `response_format=Pydantic모델` | `format=Model.model_json_schema()` |
| 파싱 | SDK가 자동으로 `parsed` | `Model.model_validate_json(response.message.content)` 직접 |
| 신뢰도 | 스키마를 거의 어기지 않음 | 모델·양자화에 따라 다름 → 검증이 더 중요 |
| refusal | 있음 | 없음 |

- Case K: `ollama.chat(..., format=SentimentResult.model_json_schema())`로 "가격 대비 훌륭한 성능" → 긍정(0.95).
- Case L: Ollama의 OpenAI 호환 엔드포인트(`base_url="http://localhost:11434/v1"`)로 OpenAI용 코드를 그대로 재사용. 다만 `json_schema` 지원은 Ollama 버전에 따라 다를 수 있다.

## 5. 검증-재시도 패턴 (Case M)

```python
for attempt in range(1, max_retries + 1):
    raw = llm_call_fn(current_prompt)
    try:
        parsed_json = json.loads(raw)                 # 1) JSON 문법 확인
    except json.JSONDecodeError as e:
        current_prompt = f"{prompt}\n[이전 응답 문제] {e}\n..."   # 오류를 알려 주고 다시
        continue
    try:
        return schema_model.model_validate(parsed_json)   # 2) 스키마 확인
    except ValidationError as e:
        current_prompt = f"{prompt}\n[스키마 검증 실패] {e}\n..."
```

실제 LLM 대신 순서대로 틀린 답을 주는 목업으로 확인했다: 1차 JSON 문법 오류(끝의 쉼표) → 2차 `age: "서른"` 타입 오류 → 3차 성공. **무엇이 틀렸는지 알려 주고 다시 요청**하는 것이 핵심이다.

## 6. GPT vs EXAONE 같은 리뷰 비교 (Case N)

리뷰: "생각보다 화면이 크고 선명해서 만족스러워요. 다만 배터리가 반나절 밖에 안 가는건 아쉽네요."

| 모델 | 분류 | 확신도 |
|---|---|---|
| GPT-4o-mini | 중립 | 0.75 |
| EXAONE 3.5 | 긍정 | 0.75 |

장단점이 섞인 문장은 모델마다 판단이 갈렸다. 형식(스키마)은 둘 다 지켰지만 **내용은 다르다**. 분류 기준("장점과 단점이 함께 있으면 중립")을 프롬프트에 명확히 적어야 결과가 일관된다. `confidence`도 모델이 스스로 매긴 숫자라 확률처럼 믿으면 안 된다.

## 정리

| 상황 | 고를 방법 |
|---|---|
| 정해진 데이터 추출·분류 | Pydantic + `.parse()` |
| 다른 도구들과 함께 쓰는 에이전트 | Function calling(`pydantic_function_tool` + `tool_choice`) |
| 긴 응답을 화면에 점진적으로 | 스트리밍 + `get_final_completion()` |
| 로컬·오픈소스 모델 | Ollama `format` + 검증-재시도 |

체크리스트: Pydantic 기본 사용 · 없을 수 있는 값은 `X | None = None` · 분류는 Enum/Literal · `refusal` 먼저 확인 · 스키마는 평평하게(중첩 최대 5단계) · **형식이 맞아도 내용은 따로 검증**

## 🔁 복습 질문

<details>
<summary>1. <code>json_object</code> 모드와 <code>json_schema</code> strict 모드의 차이는?</summary>

`json_object`는 문법상 올바른 JSON만 보장하고 필드 구성은 보장하지 않는다. strict 모드는 스키마의 필드와 타입을 지키도록 보장한다.
</details>

<details>
<summary>2. <code>.parse()</code>를 쓰면 무엇이 편해지나?</summary>

Pydantic 모델을 넘기면 SDK가 JSON Schema를 만들고 응답도 파싱해서 `message.parsed`에 객체로 돌려준다. 스키마 dict를 손으로 쓰지 않아도 된다.
</details>

<details>
<summary>3. 감성 분류에 자유 문자열 대신 Enum을 쓰는 이유는?</summary>

정해진 값(긍정/부정/중립)만 나오게 강제해서 "긍정적" 같은 변형 값이 생기지 않는다.
</details>

<details>
<summary>4. strict 모드에서 <code>phone: str | None = None</code>은 "필드가 빠질 수 있다"는 뜻인가?</summary>

아니다. 필드는 항상 있고, 값이 `null`일 수 있다는 뜻이다. strict 모드는 모든 필드가 `required`다.
</details>

<details>
<summary>5. <code>.parsed</code>를 쓰기 전에 <code>.refusal</code>을 확인하는 이유는?</summary>

모델이 안전상 응답을 거부하면 스키마 대신 `refusal`에 사유가 들어오고 `parsed`는 비어 있다. 확인하지 않으면 None을 객체처럼 쓰다 오류가 난다.
</details>

<details>
<summary>6. 로컬 모델에서 검증-재시도가 특히 중요한 이유는?</summary>

OpenAI처럼 서버가 스키마를 강제하지 않아서, 작은 모델일수록 JSON을 깨뜨리거나 타입을 틀리게 채울 수 있다.
</details>

<details>
<summary>7. 같은 리뷰를 GPT는 중립, EXAONE은 긍정으로 분류한 것에서 배울 점은?</summary>

구조화 출력은 형식만 맞춰 줄 뿐 판단까지 맞춰 주지 않는다. 경계가 애매한 경우의 분류 기준을 프롬프트에 적고, 중요한 결과는 사람이 검토한다.
</details>
