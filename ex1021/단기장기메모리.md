# LangChain 단기 메모리와 장기 메모리: checkpointer, store, PostgreSQL 영구 저장

> **한눈에 보기**
> - **단기 메모리** = 채팅방(`thread_id`) 안의 대화 기록. `create_agent(..., checkpointer=InMemorySaver())` 한 줄이면 **자동** 저장·복원
> - **장기 메모리** = 사용자별 메모장. `store=InMemoryStore()` + `namespace=("users", user_id)` / `key`로 **도구나 코드가 직접** `put`·`get`
> - 같은 방이면 단기로 기억, **새 방에서도 기억하려면 장기** 메모리가 필요하다 (성적표: 없음 ❌❌ / 단기 ✅❌ / 단기+장기 ✅✅)
> - `InMemory*`는 프로그램을 끄면 사라진다 → `PostgresSaver` / `PostgresStore`로 바꾸면 **커널을 재시작해도 남는다**. 에이전트 코드는 그대로
> - 개인 정보를 저장한다면 **삭제 수단**(`delete_thread`, `store.delete`)도 같이 만든다

- 코드: [`exam6.ipynb`](exam6.ipynb) (강사님 자료 `fwedu/exam6.ipynb` 사본, 강의 슬라이드 이미지 포함, 📝 정리 셀 추가)
- 실행 환경: langchain 1.4.x, langgraph 1.2.x, langgraph-checkpoint-postgres, PostgreSQL(도커 `edupgvector`, `edu/1234/edudb`), `gpt-4o-mini`
- 이전에 배운 것: [10/12 대화 기록 유지(`previous_response_id`)](../ex1012/LLM연동하기.md), [9/18 대화 메모리(책)](../ex0918/대화메모리.md)

## 1. thread = 채팅방

| 카톡 | LangChain |
|---|---|
| 채팅방 | thread |
| 채팅방 번호 | `thread_id` |
| 방 안에 쌓인 대화 | **단기 메모리** (messages) |
| 다른 방 | 다른 `thread_id` → 빈 대화 |

"하나의 대화 안" = **같은 `thread_id`로 호출하는 범위**다. 프로그램을 끄지 않아도 `thread_id`만 바꾸면 AI는 앞 대화를 모른다.

## 2. ① 메모리 없음 → ② 단기 메모리

```python
agent_none  = create_agent(model, tools=[], system_prompt=SYSTEM, context_schema=Context)
agent_short = create_agent(model, tools=[], system_prompt=SYSTEM,
                           checkpointer=InMemorySaver(), context_schema=Context)
agent_short.invoke({"messages": [...]}, {"configurable": {"thread_id": "A"}})
```

| 상황 | 결과 |
|---|---|
| 메모리 없음: "저는 둘리, 취미는 등산" → "제 이름과 취미?" | ❌ 방금 말했는데 모름 |
| 단기, 같은 방 A | ✅ "둘리, 등산" |
| 단기, 새 방 B | ❌ 모름 |
| B에서 "저는 도우너, 게임" 후 다시 A | ✅ "둘리" (B 방 내용과 섞이지 않음) |

`agent.get_state({"configurable": {"thread_id": "A"}})`로 보면 A 방에는 메시지 6개(human/ai 3쌍)가 그대로 들어 있다. **단기 메모리의 정체는 이 리스트를 매번 모델에게 다시 보내는 것**이다. 그래서 대화가 길어지면 토큰과 비용이 계속 늘어난다(→ [미들웨어의 요약](미들웨어.md#3-summarizationmiddleware-긴-대화-자동-요약)).

## 3. ③ 장기 메모리: store (LLM 없이)

```python
store = InMemoryStore()
store.put(("users", "dooly"), "profile", {"name": "둘리", "hobby": "등산"})   # namespace, key, value
store.get(("users", "dooly"), "profile").value     # {'name': '둘리', 'hobby': '등산'}
store.get(("users", "douner"), "profile")          # None (없으면)
store.search(("users", "dooly"))                   # 서랍 안 전체 목록
```

namespace = 서랍 이름, key = 파일 이름, value = 내용(dict). **`thread_id`와는 상관이 없다.**

## 4. ④ 단기 + 장기 에이전트

```python
@tool
def save_user_info(name: str, hobby: str, runtime: ToolRuntime[Context]) -> str:
    """사용자가 자신의 이름과 취미를 알려주면 장기 메모리에 저장합니다."""
    runtime.store.put(("users", runtime.context.user_id), "profile", {"name": name, "hobby": hobby})
    return "장기 메모리에 저장했습니다."

agent_long = create_agent(model, tools=[save_user_info, get_user_info], system_prompt=LONG_SYSTEM,
                          checkpointer=InMemorySaver(), store=long_store, context_schema=Context)
ask(agent_long, "...", thread_id="tue", user_id="dooly")    # context=Context(user_id=...)로 사용자 전달
```

- `ToolRuntime`이 도구 안에서 `runtime.store`(저장소)와 `runtime.context`(지금 누구와 대화 중인지)를 꺼내 쓰게 해 준다. 모델에게 보이는 인자는 `name`, `hobby`뿐이다.
- 월요일 방(mon)에서 저장 → 화요일 **새 방(tue)**에서 "제 이름과 취미?" → 모델이 `get_user_info`로 Store를 읽어 "둘리, 등산" ✅. 같은 새 방이라도 **다른 사용자(또치)**는 서랍이 달라 "저장된 정보가 없습니다".
- 저장할지 말지는 **모델이 판단**한다. 그래서 시스템 프롬프트에 "자기 정보를 알려 주면 save_user_info로 저장하라"를 분명히 적었다.

**성적표** (매번 새 `thread_id`/`user_id`로 같은 시나리오, 답에 "둘리"가 있으면 ✅)

| 에이전트 | 같은 대화 안 | 새 대화에서 |
|---|---|---|
| ① 메모리 없음 | ❌ | ❌ |
| ② 단기 (checkpointer) | ✅ | ❌ |
| ③ 단기 + 장기 (checkpointer + store) | ✅ | ✅ |

## 5. ⑥ PostgreSQL에 영구 저장

| | 메모리 (휘발) | PostgreSQL (영구) |
|---|---|---|
| 단기 | `InMemorySaver()` | `PostgresSaver.from_conn_string(DB_URI)` |
| 장기 | `InMemoryStore()` | `PostgresStore.from_conn_string(DB_URI)` |
| 처음 한 번 | - | `.setup()`이 테이블 생성 |
| 에이전트 | `create_agent(..., checkpointer=, store=)` | **똑같음** |

- **1차 실행**: `with pg_agent() as (agent, cp, st):`로 연결해 "저는 엘사, 취미는 스케이팅"을 저장하고 `with`가 끝나며 연결이 닫힘(= 프로그램 종료).
- **2차 실행**(새 연결·새 에이전트): 같은 방 `db-mon`은 checkpoints에서 메시지 6개가 복원되어 답했고, 새 방 `db-tue`는 store에서 읽어 "엘사, 스케이팅" ✅.
- **커널 재시작 후 3차 실행**: db-mon에서 복원된 메시지가 **8개**로 늘어 있었다(2차 실행의 질문·답이 쌓임). 그리고 db-tue에서는 이번에 `get_user_info`가 **호출되지 않았다** — 2차 실행 때 그 방에 쌓인 대화(단기 메모리)에 답이 이미 있었기 때문이다. 장기 메모리를 시험하려면 **처음 쓰는 방 번호**로 물어봐야 한다.
- DB 안을 SQL로 보니 테이블이 `checkpoints`, `checkpoint_blobs`, `checkpoint_writes`, `checkpoint_migrations`(단기)와 `store`, `store_migrations`(장기)로 생겼다. `store` 행은 `users.db-elsa / profile → {'name': '엘사', 'hobby': '스케이팅'}`.
- 실습 뒤 `cp.delete_thread("db-mon")`, `st.delete(("users", "db-elsa"), "profile")`로 지웠다 → 다시 조회하면 `None`.

## 정리

| | 단기 메모리 | 장기 메모리 |
|---|---|---|
| 붙이는 곳 | `create_agent(checkpointer=...)` | `create_agent(store=...)` |
| 호출 때 필요한 것 | `config={"configurable": {"thread_id": ...}}` | `context=Context(user_id=...)` |
| 저장하는 주체 | LangGraph가 자동 | 도구/코드가 `store.put()` |
| 저장되는 것 | 모든 메시지 원문 | 고른 핵심 정보 |
| 길어지면 | 토큰·비용 증가 → 요약 필요 | 필요한 것만 꺼내 가벼움 |

두 메모리는 대체 관계가 아니라 **보완 관계**다. 대화 흐름은 단기, 오래 기억할 사실은 장기.

## 🔁 복습 질문

<details>
<summary>1. 단기 메모리에서 "같은 대화"를 구분하는 값은?</summary>

`thread_id`. 같은 값으로 부르면 이전 메시지를 불러오고, 다른 값이면 빈 대화가 된다.
</details>

<details>
<summary>2. 단기 메모리만 있는 에이전트가 새 방에서 이름을 모르는 이유는?</summary>

checkpointer는 thread 단위로 메시지를 저장한다. 새 `thread_id`에는 저장된 메시지가 없으니 모델에게 보낼 기록도 없다.
</details>

<details>
<summary>3. 장기 메모리의 namespace에 사용자 ID를 넣는 이유는?</summary>

사용자별로 서랍을 나눠, 다른 사용자의 정보를 읽거나 덮어쓰지 않게 하려고. 같은 방 번호라도 사용자가 다르면 다른 서랍을 본다.
</details>

<details>
<summary>4. 도구 함수에서 <code>runtime: ToolRuntime[Context]</code>는 무엇을 해 주나?</summary>

도구 안에서 `runtime.store`(저장소)와 `runtime.context`(호출 때 넘긴 user_id 등)에 접근하게 해 준다. 모델은 이 인자를 보지 않는다.
</details>

<details>
<summary>5. 커널을 재시작해도 기억이 남게 하려면 무엇을 바꾸나?</summary>

`InMemorySaver` → `PostgresSaver`, `InMemoryStore` → `PostgresStore`. 처음 한 번 `.setup()`으로 테이블을 만들고, 에이전트 코드는 그대로 둔다.
</details>

<details>
<summary>6. 재시작 후 db-tue 방에서 get_user_info가 불리지 않은 이유는?</summary>

그 방에는 이전 실행의 대화가 DB(단기 메모리)에 남아 있어서, 모델이 대화 기록만 보고 답할 수 있었기 때문이다.
</details>
